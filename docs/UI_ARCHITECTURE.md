## Component and style boundaries

Group related components, CSS Modules, and helpers under their feature in `components/`. Profile owns its editor and styles, borrowing owns My Activity and the calendar, listings owns the editor, camera, and browser photo processing, marketplace owns Explore, My Listings, and tool detail, and notifications owns Updates. The dashboard shell and its view dispatcher live together. Shared primitives belong in `components/ui/`, shared hooks in `hooks/`, and cross-feature helpers in `lib/`.

1. **Reuse the nearest component.** Inspect callers and the current DOM before creating a parallel implementation. ToolCard serves Explore and My Listings. ListingForm handles both creation and editing. RequestList handles both activity roles. DashboardShell owns persistent navigation.
2. **Extend a variant when the behavior is already shared.** The Button uses `class-variance-authority`, `cn` and Radix Slot. Keep its existing variants and semantics in view before extending it. Use a scoped class for a difference confined to one composition, such as Explore's price chip.
3. **Keep feature-specific behavior local.** BorrowCalendar, CameraCapture and the Profile editor have workflow state and a known owner. Extract a shared component when multiple real callers need the same structure and interaction contract. Compose route-specific layouts from these components.
4. **Keep route files thin.** Server layouts own auth entry and shell selection. Route pages own metadata, parameters and composition. Put Convex hooks in the feature component that owns the displayed data and actions. Leave static editorial content on the server.
5. **Use utilities for simple styling.** Reuse the existing shadcn primitives and their variants when they fit the interaction. Use Tailwind in `className` for simple styling and a colocated CSS Module for complex or repeated rules within a feature. Share a class or component when multiple callers need the same styling. Use `cn` when merging utility variants or caller overrides. Use native state selectors such as `[aria-current]`, `[aria-pressed]`, `:focus-visible`, `:disabled` and `[open]` when they express the state.
6. **Follow the cascade and preserve responsive behavior.** Check later selectors and inclusive media queries before adjusting a shared rule. Keep styles mobile-first in behavior and verify the actual breakpoints. Global CSS remains the home for project tokens and shared rules. Profile, My Activity, Explore, My Listings, tool detail, Listing Studio, Updates, and Loan Detail use Tailwind for simple layout and colocated CSS Modules for custom styling. Profile shares field styles with Loan Detail. The homepage loads its page, scroll story, and catalog styles from their respective entry points. The story keeps its existing selectors for GSAP and browser tests. Keep feature-local motion in CSS unless the existing feature needs DOM measurement, as the dashboard indicator does.
7. **Keep styling changes scoped.** Avoid global overrides for one route, shadow copies of shared components, alternate palettes, broad replacements of native controls and production fixtures. When a new convention is deliberate, document its component, scope and responsive/accessibility behavior.

## Data and presentation

Clerk owns identity. [proxy.ts](../proxy.ts) supplies the request context, protected Next layouts call `auth.protect()`, and Convex authenticates its own queries and mutations. [useCurrentProfile](../hooks/use-current-profile.ts) waits for Convex authentication, queries `users.me` and bootstraps a missing profile with `users.ensureCurrent`. DashboardShell redirects a profile without a society to onboarding. Its conditional Admin link is a UI affordance. Backend authorization still controls reads and writes.

Convex shapes data for each viewer. [tools.ts](../convex/tools.ts) produces authenticated tool views with authorized photo URLs, display fields, proximity, visibility and ownership flags. Its public projection and validator contain exactly `name` and `category`. Keep the public catalog and fictional marketing radius separate from Explore's authenticated discovery. The UI formats distances, labels and INR prices from the view. When the selected ID is outside the bounded active society results, Explore shows “Your society” and Profile shows “Your selected society”.

[requests.ts](../convex/requests.ts) projects participant-facing names, status, negotiation amounts and timestamps, loan state and applicable conflict information. It owns availability and transaction checks. UI date and price estimates help the person fill out the form. Convex remains authoritative for Kolkata calendar days, pricing, overlap, reservation and state transitions. A pending request never reserves a date. Keep request and loan progression tied to recorded events.

[loans.ts](../convex/loans.ts) returns handover data only to the loan's participants. [handover.ts](../convex/handover.ts) holds the current user's reusable private fields. Profile edits those saved fields. Loan detail lets a participant select fields to share for that loan or edit the loan-specific details. Keep saved details and private handover fields out of catalog, listing, request, admin and automation props. Admin access and moderation, including trust assignment and audit writes, remain in [admin.ts](../convex/admin.ts). [automation.ts](../convex/automation.ts) supplies notification and delivery views. Loan status comes from the loan itself.

Listing Studio holds local form values, object URLs and upload progress. [image-processing.ts](../components/listings/image-processing.ts) prepares files and uploads with progress. Convex owns listing validation, photo tickets/registration/attachment and visibility. Preserve staged creation, retained draft state on failure, ordered attachment and retry behavior. Use `undefined` for the unresolved query state, and honor resolved empty or unavailable responses. Keep mutation errors visible near their action. Avoid supplying invented records or optimistic status claims just to populate a design.

## Page patterns

| Route or flow                                                         | UI owner and conventions                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public landing `/`                                                    | Home composes MarketingHeader (overlaid on the story at desktop sizes)/Footer, ScrollStory, SocietyShowcase and PublicCatalog. Six readable chapters follow one continuous drill from cupboard to neighbor and back. Benefits, trust and catalog move to the paper canvas. Keep the radius demo explicitly fictional. Journal and Communities share the editorial shell.                          |
| Sign-in, sign-up and onboarding                                       | [AuthPage](../components/auth/auth-page.tsx) supplies the shared panel and styles for Clerk Sign In, Clerk Sign Up, and the Onboarding error boundary. The panel heading and Clerk card fit within narrow screens. [Onboarding](../components/onboarding/onboarding.tsx) combines explanatory copy with society search, a native suggestion disclosure and readable status. Keep Clerk redirects and the distinction between selected societies and pending suggestions.                                                                                                |
| Explore `/dashboard`                                                  | [ExploreTools](../components/marketplace/explore.tsx). Local Shelf heading, selected society, List an item, a search bar with the distance picker, a price/category/sort row, then uniform cards. Preserve `scope`, `text`, optional `category`, `price` and `sort` query arguments and reset defaults.                                                                              |
| Tool detail `/dashboard/tools/[id]`                                   | [ToolDetail](../components/marketplace/tool-detail.tsx) composes breadcrumb, gallery, facts, lender and borrow form. Owner view substitutes visibility, edit and manage actions and omits the borrower instructions. Keep gallery order and the mobile calendar clear of bottom navigation.                                                                                                                                                  |
| My Listings `/dashboard/listings` and Studio routes                   | [My Listings](../components/marketplace/my-listings.tsx) supplies ToolCard owner actions and visibility badges. [ListingForm](../components/listings/listing-form.tsx) uses the same editor for `/dashboard/listings/new` and `/dashboard/listings/[id]/edit`. The editor keeps the live preview visible and submits directly through Publish listing or Save changes. Keep cover selection and order, camera fallback and retry in this flow.                                                                                           |
| My Requests and Incoming `/dashboard/requests`, `/dashboard/incoming` | `RequestList({ incoming })` in [borrowing.tsx](../components/borrowing/borrowing.tsx). One My Activity destination, two route links and a completed-returns filter. Render each role's labels, recorded progress and available actions.                                                                                                                                                                     |
| Negotiation                                                           | Paid tool detail starts the standard request or offer. Activity shows price history and permitted decisions. The lender's one final counteroffer uses the existing native dialog. Keep the proposed and agreed totals distinct.                                                                                                                                                                   |
| Loan detail `/dashboard/loans/[id]`                                   | [LoanDetail](../components/borrowing/loan-detail.tsx). Reservation summary and return action, participant-only handover, lifecycle timeline and separate delivery records. | Updates `/dashboard/notifications`                                    | [Notifications](../components/notifications/notifications.tsx) renders a narrow list with message, status and Kolkata time. Use activity links in the empty state.                                                                                                                                                                                                                                              |
| Profile `/dashboard/profile`                                          | [Profile](../components/profile/profile.tsx) pairs a dark identity card with private saved handover fields. Header link remains the route entry. Trust labels reflect admin-assigned flags.                                                                                                                                                                                                               |
| Admin `/admin` and its sections                                       | [Admin](../components/admin/admin.tsx) renders Overview, Users, Listings, Loans, Societies, Suggestions, Audit and Automation in its own shell. Use bounded queries and visible Load more behavior. Most text/status filters operate on loaded results. The Automation status filter is sent to Convex. Overview counts are capped at 1,000. Keep the data scope and moderation confirmations explicit. |

## Visual verification

Use the [development setup](DEVELOPMENT.md) for configuration. For meaningful visual changes, check Chromium at 360, 390, 768, 1280 and 1440px. Check relevant breakpoint edges and look at focus, selected, disabled, loading, empty, error and reduced-motion states in addition to the default screen. Capture affected desktop and mobile views with Playwright and review the images before changing baselines.

```bash
npm run dev
# In a second terminal, with the server at http://localhost:3000
npx playwright test tests/e2e/public.spec.ts
node tests/visual/atlas-qa.mjs
npx vitest run tests/contrast.test.ts
```

- **Public browser tests** use the actual Next routes and cover story motion, viewport overflow, touch emulation, keyboard and reduced motion, static narrative, journal navigation and protected-route redirect. Captures go under `test-results/`. The landing screenshot comparison runs on macOS. See [the public snapshots directory](../tests/e2e/public.spec.ts-snapshots).
- **Atlas fixture renderer** bundles current Onboarding, Dashboard and Admin components and serves the HTML in intercepted browser requests. It loads the actual app CSS and font definitions, bundles component CSS Modules, and stubs Clerk, Convex and Next navigation. Use the real routes to check URL and auth behavior. Fixture paths can differ from route paths, such as Admin Listings. There is no Next.js `/__atlas-qa` route. Use the fixtures for appearance and interaction mechanics only. The `shelf` view renders the homepage PublicCatalog with stubbed name/category rows and checks the swipe carousel at 390px and the pinned track at 1440px. Regenerated screenshots go under `artifacts/atlas/` at the five audit widths. The [visual catalog](DESIGN_SYSTEM.md#visual-component-catalog) lists representative views and states.
- **Live authenticated coverage** requires isolated Clerk test identities and a development Convex deployment. Keep protected routes, session-token integration and mutation paths intact. Run the appropriate authenticated specs for changes to those paths. Never wire fixture logic into an app route or point test mutations at production.
- **This audit** used Chromium on the running local Next app for homepage, catalog, public editorial pages, sign-in/sign-up shells and protected redirects. The 11 public tests and 70 protected fixture page/viewport renders passed. Computed style samples covered typography, grid, borders, focus, hover and disabled controls. The protected fixture run covered Explore, listings/detail, Studio, both activity lists, loan, Updates, Profile, admin Overview and admin Listings. Authenticated production-equivalent rendering, the Clerk account menu, live transactions and populated admin sections beyond Overview/Listings remain outside this audit. Other component behavior is labeled as source-derived where applicable.

For prior implementation QA, see [Phase 7](PHASE7_QA.md) and [Atlas](ATLAS_QA.md). For backend contracts see [architecture](ARCHITECTURE.md) and [security and privacy](SECURITY_AND_PRIVACY.md).
