# Security and privacy — Phase 1

| Data                                                               | Why and where                                                                | Access                                                                                                     |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Clerk identity and session                                         | Authentication in Clerk                                                      | Clerk and the signed-in user                                                                               |
| Clerk subject, display name, selected society ID                   | Minimal Convex profile and onboarding                                        | The signed-in user through authenticated Convex functions; operators through deployment administration     |
| Role and two trust flags                                           | Future moderation and trust foundation in Convex; default `user`/false/false | LendLoop operators only for changes; no user mutation accepts these fields                                 |
| Society name, city, locality and independently sourced coordinates | LendLoop directory in Convex                                                 | Public active-society search exposes name, city and locality only; coordinates stay out of query responses |
| Pending society suggestion                                         | Let signed-in users propose missing societies                                | Stored in Convex for operator review; no public listing query                                              |
| Active tool name and category                                      | Public catalog                                                               | Public query returns only these two fields                                                                 |

The app does **not** collect a private address, phone number, GPS location/history, payment details, or full Clerk profile in Phase 1. Society choice is self-declared and does not verify residency. Browser geolocation is not used. Secrets are kept in ignored local files or service environment settings, never in source control. The application does not intentionally log private profile data or secrets.

Convex functions enforce authentication and allowed mutations on the server. `users.ensureCurrent` keys on the stable Clerk subject and always creates a normal user with both badges false. `users.selectSociety` verifies active status. Society suggestions always start pending. No public function creates/approves societies or writes tools. The public catalog maps records to only name and category, even though tool records contain more fields.

**Implemented in Phase 3:** private handover details appear only after approval and only to the loan participants. Retention/deletion procedures, operator audit logs and moderation authorization remain planned before production launch.

## Phase 2 listing photos and access

Only signed-in, society-onboarded users can create listings or upload photos. Convex derives owner and society from the authenticated Clerk subject and enforces owner checks for listing edits, status changes and photo attachment/removal. Upload tickets are owner-bound and expire after ten minutes; registration checks the storage record's age, SHA-256 fingerprint, size, MIME type and file signature/ending, and rejects already claimed IDs. Listings accept at most five distinct photo IDs. The browser decodes and re-encodes supported images as JPEG at up to 1600 px, which removes EXIF including GPS. Original files above 5 MB and HEIC/HEIF are rejected. Backend checks do not rely only on a filename or browser MIME claim.

Convex File Storage URLs are bearer URLs: anyone with a URL can share it. The app gives URLs only to authenticated marketplace queries. The unauthenticated catalog returns only name and category; it never returns owner IDs, location, prices, storage IDs or image URLs. Photo URLs should not be treated as confidential documents. Daily cleanup removes unreferenced storage files and expired ticket records older than 48 hours. The sweeper assumes this deployment's file storage is for listing photos; update it before adding another file type. The owner removes a photo by saving a listing without it; archiving keeps photos for future transaction history. Camera permission is requested after a deliberate action, audio is never requested, and stream tracks stop on close or unmount. Browser camera APIs require a secure context; native capture behavior varies by device.

## Phase 3 borrowing privacy

Every borrowing mutation and private query authenticates the Clerk identity and requires society onboarding. Borrower and lender IDs are derived server-side; clients cannot provide or change them. Pending request lists contain only limited display names, listing imagery, dates, prices and status. They never return email, phone, addresses or private profiles. Approval creates a loan only after a transactional availability check. Loan detail and handover data require matching borrower/lender IDs; unrelated users receive no loan detail and cannot mutate it. An optional contact phone, pickup point and instructions are stored separately per participant and may be deleted by clearing the form. A complete residential address, GPS trail, identity document and payment details are not requested. The users table remains minimal. Loan terms and timestamps persist for history; a formal retention and deletion policy is still needed.
