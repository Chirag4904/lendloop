# Security and privacy — Phase 1

| Data                                                               | Why and where                                             | Access                                                                                                                  |
| ------------------------------------------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Clerk identity and session                                         | Authentication in Clerk                                   | Clerk and the signed-in user                                                                                            |
| Clerk subject, display name, selected society ID                   | Minimal Convex profile and onboarding                     | The signed-in user through authenticated Convex functions; operators through deployment administration                  |
| Role and two trust flags                                           | LendLoop moderation in Convex; default `user`/false/false | Admins change trust flags; deployment operators provision the first admin; ordinary profiles cannot change these fields |
| Society name, city, locality and independently sourced coordinates | LendLoop directory in Convex                              | Public active-society search exposes name, city and locality only; coordinates stay out of query responses              |
| Pending society suggestion                                         | Let signed-in users propose missing societies             | Stored in Convex for operator review; no public listing query                                                           |
| Active tool name and category                                      | Public catalog                                            | Public query returns only these two fields                                                                              |

The app does **not** collect a private address, phone number, GPS location/history, payment details, or full Clerk profile in Phase 1. Society choice is self-declared and does not verify residency. Browser geolocation is not used. Secrets are kept in ignored local files or service environment settings, never in source control. The application does not intentionally log private profile data or secrets.

Convex functions enforce authentication and allowed mutations on the server. `users.ensureCurrent` keys on the stable Clerk subject and always creates a normal user with both badges false. `users.selectSociety` verifies active status. Society suggestions always start pending. Only authenticated LendLoop admins can create or approve societies; normal users can create only their own listings. The public catalog maps records to only name and category, even though tool records contain more fields.

Private handover details appear only after approval and only to loan participants. Phase 6 adds admin audit and moderation authorization. Retention and deletion procedures remain planned before production launch.

## Phase 2 listing photos and access

Only signed-in, society-onboarded users can create listings or upload photos. Convex derives owner and society from the authenticated Clerk subject and enforces owner checks for listing edits, status changes and photo attachment/removal. Upload tickets are owner-bound and expire after ten minutes; registration checks the storage record's age, SHA-256 fingerprint, size, MIME type and file signature/ending, and rejects already claimed IDs. Listings accept at most five distinct photo IDs. The browser decodes and re-encodes supported images as JPEG at up to 1600 px, which removes EXIF including GPS. Original files above 5 MB and HEIC/HEIF are rejected. Backend checks do not rely only on a filename or browser MIME claim.

Convex File Storage URLs are bearer URLs: anyone with a URL can share it. The app gives URLs only to authenticated marketplace queries. The unauthenticated catalog returns only name and category; it never returns owner IDs, location, prices, storage IDs or image URLs. Photo URLs should not be treated as confidential documents. Daily cleanup removes unreferenced storage files and expired ticket records older than 48 hours. The sweeper assumes this deployment's file storage is for listing photos; update it before adding another file type. The owner removes a photo by saving a listing without it; archiving keeps photos for future transaction history. Camera permission is requested after a deliberate action, audio is never requested, and stream tracks stop on close or unmount. Browser camera APIs require a secure context; native capture behavior varies by device.

## Phase 3 borrowing privacy

Every borrowing mutation and private query authenticates the Clerk identity and requires society onboarding. Borrower and lender IDs are derived server-side; clients cannot provide or change them. Pending request lists contain only limited display names, listing imagery, dates, prices and status. They never return email, phone, addresses or private profiles. Approval creates a loan only after a transactional availability check. Loan detail and handover data require matching borrower/lender IDs; unrelated users receive no loan detail and cannot mutate it. An optional contact phone, pickup point and instructions are stored separately per participant and may be deleted by clearing the form. A complete residential address, GPS trail, identity document and payment details are not requested. The users table remains minimal. Loan terms and timestamps persist for history; a formal retention and deletion policy is still needed.

## Phase 4 negotiation privacy

Offer and counteroffer prices appear only in borrower and lender request queries. Convex mutations derive the acting participant from Clerk and check request status before every price decision; the client cannot supply another participant or an agreed price. Counteroffer bounds and integer-paise precision are enforced server-side. Final acceptance rechecks listing activity and overlapping loans. Confirmed loan prices cannot be edited. Negotiation data does not enter the unauthenticated catalog, handover details, logs, analytics or third-party services.

## Phase 5 automation data flow

Each successful transition inserts a minimal Convex outbox event. The dispatch action sends event ID (deduplication), type (template selection), recipient user ID (routing), request ID (correlation), item name (readable mock message), and lease (acknowledgement authority) to the signed n8n webhook. It sends no phone, home address, handover instructions, Clerk credential, complete profile, or borrowing history. The 09:00 IST n8n schedule calls a signed Convex HTTP action that returns only eligible loan IDs and the Kolkata date. Convex owns the overdue rule and creates a unique `overdue:<loanId>:<date>` reminder claim. n8n signs each claim and completion request; it receives only the key and lease. The mock reminder is visible in the borrower's notification center only after completion is acknowledged.

Separate development secrets protect Convex → n8n and n8n → Convex traffic. The exact signing specification is in the README. Convex validates method, path and query, timestamp, nonce, signature and raw body before a service operation, records accepted nonces transactionally, and rejects replay. n8n verifies the incoming signature with constant-time comparison and a five-minute window; Convex's event ID and lease make a repeated webhook harmless. An attacker without either shared secret cannot claim a reminder or record delivery. All externally reachable calls require HTTPS; neither n8n nor its exports hold a Convex admin key. Secrets live only in ignored `.env.n8n` and Convex environment variables. The public catalog still returns exactly name and category.

The outbox records retry pending or terminal failed states and sanitized codes; it never reports delivery based only on queueing. Transient dispatches have five bounded attempts with a two-minute lease and exponential backoff. A maintenance cron marks stale reminder claims failed; reruns can reclaim them without creating another daily record. n8n's error workflow logs a sanitized workflow name, execution ID, step, timestamp and short summary. Successful execution payloads are not retained; failed n8n executions are pruned after 14 days or 1,000 records. Convex retains user-facing automation history until a separate production retention policy is approved.

The self-hosted Community edition stores full node inputs for failed executions, including short-lived HMAC signature headers and minimal event payloads. It does not store the shared secrets. Restrict access to the n8n editor and persistent volume; the 14-day prune window limits this exposure. For a production environment that forbids retaining any authentication header, use n8n Enterprise execution-data redaction or disable failed execution-data saving and monitor sanitized Convex failure states and n8n server logs instead.

## Phase 6 administration and data minimization

A Clerk subject, display name, selected society, role and two manual trust flags live in Convex `users`; Clerk owns account authentication. Admin Users pages show a limited account identifier, display name, society, role, trust flags and join date, without email or phone. Admin Loans pages show participant display names, society relationship, dates, price snapshots, lifecycle and safe automation states; they do not query or return participant handover records. The public catalog remains exactly name and category. Optional handover phone, pickup point and instructions stay in `loanHandoverDetails` and are readable only by confirmed-loan participants through `loans.detail`. The n8n payload remains limited to IDs, event type, item name and lease; no admin audit, phone, address, or handover details are shared with it.

All admin mutations derive the actor from Clerk and write an audit record in the same transaction. Role and trust flags are never accepted by ordinary profile mutations. The first-admin operation is internal and requires deployment credentials; the operator identity is recorded as such because it is outside app authentication. Admin audit records are readable only by admins and have no public write function. Society deactivation and listing removal preserve historical links. LendLoop does not collect identity documents, a verified home address, GPS history, payment credentials or automatic trust scores. A formal retention/deletion policy for historical records and audit rows is still required before production launch.
